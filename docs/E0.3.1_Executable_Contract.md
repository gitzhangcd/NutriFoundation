# E0.3.1｜Chat-Window Semantic Worker Bridge, TaskBundle / ResponseEnvelope Contract, Deterministic Orchestration, Response Ingestion & Provider-Portability Freeze

## Status

`REFERENCE IMPLEMENTATION / EXECUTABLE CONTRACT FREEZE`

## Goal

E0.3.1 separates semantic inference from deterministic scientific control.

```text
Code = controller + provenance + validator + verifier + state machine
Semantic Worker = bounded semantic transformation
```

The current semantic worker may be the ChatGPT chat window. Future OpenAI / Claude / Gemini / local-model workers must use the same contract.

## Provider-neutral boundary

The only portable model interface is:

```text
TaskBundle
    ↓
SemanticWorkerAdapter
    ↓
ResponseEnvelope
```

Provider-specific code must exist only inside an adapter.

The following layers must remain provider-unaware:

- SourceArtifact persistence
- task orchestration
- response binding
- EvidenceUnit schema mapping
- deterministic verification
- F0 freeze
- ScientificClaim pipeline
- GOLD governance

## TaskBundle

`TaskBundle v0.1` is an immutable self-contained semantic request.

It binds:

- task_id
- task_type
- contract_version
- run_id
- source_id
- evidence_id
- SourceArtifact snapshot
- source text
- source-text SHA-256
- requested output fields
- frozen scientific rules
- response schema version
- task SHA-256
- provenance

No provider credential or provider-specific prompt syntax is allowed in the TaskBundle scientific contract.

## Task hash

`task_sha256` is computed from the canonical JSON payload excluding the hash field itself.

Any mutation of source text, rules, source snapshot, requested fields, evidence identity or contract version invalidates the task hash.

## ResponseEnvelope

`ResponseEnvelope v0.1` is the only semantic output accepted by the core engine.

It must echo:

- task_id
- task_sha256
- contract_version
- response_schema_version
- source_text_sha256

It also records execution-only worker metadata:

- worker_id
- adapter_type
- provider
- model
- model_version
- prompt_version

Worker metadata is provenance. It must not become scientific EvidenceUnit content.

## Response states

Allowed semantic responses:

- `completed`
- `defer`
- `failed`

`defer` is a valid outcome when the source does not support reliable extraction.

```text
SemanticUncertainty -> DeferAllowed
```

No system component may convert a deferred response into a guessed EvidenceUnit.

## Deterministic response binding

Before any response can become an EvidenceExtractionCandidate, code must verify:

```text
Response.task_id == Task.task_id
Response.task_sha256 == Task.task_sha256
Response.source_text_sha256 == Task.source_text_sha256
Response.contract_version == Task.contract_version
Response.response_schema_version == Task.response_schema_version
```

Any mismatch blocks ingestion.

## Output allowlist

For the E0.3.1 EvidenceUnit extraction task, only the frozen EvidenceUnit semantic fields may appear in `ResponseEnvelope.output`.

Unknown provider fields are rejected.

Examples of forbidden output pollution:

- API response IDs as scientific fields
- provider secrets
- chain-of-thought
- hidden model scores
- arbitrary vendor metadata

Provider metadata belongs only in WorkerDescriptor / provenance.

## Chat-window bridge

The reference chat-window adapter is file based.

```text
semantic_rpc/outbox/
    TASK.request.json

Chat window
    ↓

semantic_rpc/inbox/
    TASK.response.json
```

The chat bridge performs no scientific verification and has no F0 authority.

Its only responsibilities are:

- export immutable TaskBundle;
- import ResponseEnvelope.

## Deterministic orchestration states

```text
PENDING
  ↓
EXPORTED
  ↓
RESPONDED
  ├─> DEFERRED
  ├─> REJECTED
  ↓
INGESTED
  ↓
F0_FROZEN
```

Illegal transitions are rejected.

## Response ingestion

A completed, bound ResponseEnvelope is transformed into an EvidenceExtractionCandidate.

The core engine injects:

- source_id
- evidence_id
- candidate status
- lineage
- worker execution provenance

The semantic worker cannot set:

- frozen state
- verification status
- F0 status
- GOLD status

## Scientific verification remains unchanged

After response ingestion, the existing E0.3 verifier still checks:

- source linkage
- source-text hash
- required fields
- source anchor
- numeric support
- applicability boundary
- observational causality guard
- guideline authority guard
- extractor/verifier independence

Only verified candidates may enter F0.

Therefore:

```text
ResponseEnvelope != EvidenceUnit_F0
```

## Provider portability

A future provider adapter implements:

```python
class ProviderAdapter:
    adapter_type = "provider_name"

    def execute(self, task: TaskBundle) -> ResponseEnvelope:
        ...
```

It must pass `run_adapter_conformance(adapter, task)`.

Conformance validates:

- ResponseEnvelope schema
- adapter_type consistency
- task identity
- task hash
- source-text hash
- contract version
- response schema version

No downstream code changes are permitted merely because the provider changes.

## Persistence

E0.3.1 adds:

- `semantic_task`
- `semantic_response`
- `semantic_event`

Task payloads and response payloads are immutable.

Task state is stored separately from immutable TaskBundle content.

E0.3.1 adds:

```text
ProviderLogic -> AdapterOnly
CorePipeline != ProviderSpecific
ResponseTaskHash == TaskBundleHash
ResponseSourceTextHash == TaskSourceTextHash
ResponseContractVersion == TaskContractVersion
ResponseEnvelope != EvidenceUnit_F0
```

## Migration guarantee

Migration from chat-window execution to an API/local model must require only:

1. implement one SemanticWorkerAdapter;
2. map provider response into ResponseEnvelope;
3. pass adapter conformance tests.

The following must not change:

- TaskBundle
- ResponseEnvelope
- EvidenceUnit schema
- verifier
- F0 freeze engine
- persistence semantics
- ScientificClaim qualification
- GOLD governance

## Exit criteria

E0.3.1 passes when remote CI proves:

1. TaskBundle self-hash validation works;
2. ChatWindowFileBridge round-trips immutable tasks/responses;
3. correct ResponseEnvelope can reach F0 only through deterministic verifier;
4. wrong task hash is rejected before candidate creation;
5. unknown provider fields are rejected;
6. semantic defer creates no EvidenceUnit;
7. a fake future API adapter passes the same conformance contract;
8. adapter-type mismatch fails;
9. previous E0.1–E0.3 tests and Batch001 replay gates remain green.
